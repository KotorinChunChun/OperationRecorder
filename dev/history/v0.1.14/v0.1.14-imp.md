# OperationRecorder 0.1.14 実装計画・報告

## 設計

0.1.13の単一可視窓向け候補は従来どおりとする。追加の読み取り経路では、ログイン窓を有効なrootとし、同じPIDの可視かつ無効なWinFormsトップレベルを1枚だけ観測する。ネイティブの所有関係、クラス、可視状態と有効状態、世代、プロセス開始時刻・EXE・セッションを確認する。双方のクラス、所有関係、DPI、物理寸法と文字なしUI構造、EXEの版とSHA256を正規化して構成を識別する。診断で取得した構成を照合・審査した上で、候補取得時にそのハッシュを指定する。両方未所有の構成も明示的に別の関係として照合する。第三の可視窓、未知の所有元、背後窓の有効化・認証欄、観測中に変わる状態、未確認の構成は拒否する。

診断は所有関係、ネイティブの状態、クラス、DPI、物理矩形と文字なしの構造ハッシュを返す。画素、欄の名前や値、背後窓の表示文字、他の画面のタイトルは取得しない。候補・診断は隔離した読み取り専用プロセスとし、プロファイルの書き込みや証拠保存・操作許可の判定には接続しない。

## フェーズ

- [x] P1 実装、既存Core・追加の判定試験、版とPowerShellの整合確認。
- [x] P2 専用フォームで標準・カスタム欄と原因別拒否を検証し、既存の証拠保護を回帰試験する。成果物のSHA256と呼び出し例を記録する。

## P1の結果

0.1.13では候補と証拠の双方が単一可視rootの判定を使っていた。0.1.14では `-DiagnoseWindowLayout` と `-ReviewedWindowLayoutSha256` を候補コマンドに追加した。パスワード証拠の単一可視rootの条件を維持し、候補側でだけ2窓を確認する。それぞれの窓の構造を読み取る際に、Win32で確認した相手側のトップレベルをUIAの部分木から外す。背後窓の全体と入力候補の有効状態を確認し、標準のパスワード属性を持つ要素がある背後窓も拒否する。ログイン欄は既知の公開ラベルと欄の型・構造で一意に照合する。診断はラベル文字を照合せず、候補取得時もラベルの比較にUIAの条件検索を使う。

WinEventを含むウィンドウグラフ3回と、ネイティブ状態・UIA構造2回を比較する。グラフの世代の変化、グラフ自体に差がなくても有効状態等の観測結果が変わった場合、最後のグラフが不完全な場合は、診断で `window-layout-changed` としてハッシュなしで返す。構成を指定した候補取得でも同じ照合を行う。

Coreは661件合格。0.1.13の643件に欠落なく、追加18件で構成、構成変更の検出、引数、証拠の既存条件を検証した。証拠の回帰では、2枚目を明示承認しても可視トップレベルがある場合はパスワード証拠を拒否する。Releaseビルドの警告・エラーは0。変更したPowerShellの3ファイルは構文検査を通過した。記録は `logs/core-final-20261119/summary.json`。

## P2の結果

別プロセスのPowerShellから最終Releaseビルドを呼び、96 DPIの専用WinFormsで26応答を検証した。ログイン窓と同じクラスの無効な背後窓を作り、両窓の直接所有の2方向と、両方が未所有の3構成を診断した。構成を確認してハッシュを渡した場合は、どの構成でも標準パスワード欄と `IsPassword=false` のカスタム欄を一意に取得できた。DPI・物理枠・相対座標・UI構造ハッシュと欄の型を照合した。単一可視窓の従来呼び出しでも `candidate-only` が得られた。

| 条件 | 診断または候補の結果 |
|---|---|
| 各所有構成の無効な背後窓 | 診断は `review-required`。構成ハッシュが一致した標準・カスタム欄は `candidate-only` |
| 2窓でレビュー指定なし、誤ハッシュ、背後窓の形状変更後に旧ハッシュを指定 | `layout-unproven` |
| 16進64桁でないハッシュ | `invalid-request` |
| 背後窓が有効 | `background-window-enabled` |
| 可視の背後窓が複数 | `ambiguous-window-layout` |
| 対象2窓の外に所有元がある | `unsupported-ownership` |
| 背後窓に標準パスワード欄がある | `background-authentication-ui` |
| 本物の別PIDのHWNDを対象PIDの指定に混ぜる | `target-mismatch` |

診断で拒否した各ケースでは、構成ハッシュがなく、候補取得も拒否した。通常の候補と診断の応答に、背後窓の架空タイトル・可変テキスト・パスワード名／値や、ログイン欄の架空値は含まれなかった。画像・登録資材は作成されず、実行前後で製品ファイルのSHA256も一致した。観測中の変化はCoreで再現し、専用フォームでは診断後の構成変更により旧ハッシュが失効することを確認した。

裏窓の有効状態は、WinFormsの表示と所有設定を済ませた後のネイティブ状態で確認した。初回の専用試験では表示後も裏窓が有効だったため、試験フォームが無効状態を明示して、Win32で確かめてから試験するよう修正した。

| 試験 | 成功 | 記録 |
|---|---|---|
| Core | 661件 | `logs/core-release-20261119/summary.json` |
| PasswordLayoutBackdrop | 専用WinFormsの1テストで26応答 | `logs/layout-final-20261119/summary.json` |
| PasswordEvidence | 標準・カスタム欄をWGCで保護する既存1件 | `logs/regression-PasswordEvidence-20261119/summary.json` |
| WindowTransition | 切替と保護の既存1テストで8ケース | `logs/regression-WindowTransition-20261119/summary.json` |

最終試験の失敗・スキップは0。4プロジェクトのReleaseビルドの警告・エラーは0。ケース表は445メソッド・728ケース。
