# OperationRecorder 0.1.15 実装計画・報告

## 設計

2026-11-20の実際の対象アプリのログでは、診断24回のうち `window-layout-changed` が18回、`background-structure-unproven` が6回だった。このログにはUIA側の有効状態や失敗枝がなく、原因は確定できなかった。

0.1.14で同じ結果にまとめていた構造取得不能とWin32/UI Automationの有効状態の食い違いを区別する。既存のステータス、`diagnostics.reason`、PowerShell引数を維持し、診断を指定したときだけ追加の構造・再観測情報を返す。UIA観測の内訳は固定コード、対象窓の役割、ルートの有効状態、観測要素数・深さと上限に限定する。再観測は従来の拒否条件を保ち、差を検知した段階と項目の種類を返す。再観測で不一致があった応答には、構成確認に使えるハッシュを含めない。

専用WinFormsでWin32とUI Automationの食い違いを調べる。読み取り候補の調整は、通常のWinFormsで食い違いが再現し、同じPID・世代・所有元でWin32の無効状態と完全なUIA構造が確認できる条件に限る。実際の再現と判断は結果に記録する。既存のマスク済み証拠、撮影許可、認証画面や未知窓の拒否は従来の条件で評価する。

専用フォームの予備測定では、WinFormsの `Enabled=true` を保ったままネイティブの `EnableWindow(false)` を実行すると、Win32は無効、UIAは有効を返した。この方向の不一致に限り、2窓の既存条件、Win32無効状態の再確認、完全なUIA構造と可視子ウィンドウの照合、認証候補の不在を満たせば、候補専用の構成ハッシュを発行する。生のUIA有効状態を構造ハッシュに含めるため、通常無効状態のハッシュを転用できない。不一致時は背後窓のEdit・Custom・欄と判定したPaneが、有効状態にかかわらず候補を妨げる。

## P1の結果

`diagnostics.loginStructure` と `diagnostics.backgroundStructure` にルートのWin32/UIA有効状態、観測した要素数と深さ、上限、固定コードを返した。失敗側が分かれば `failureRole` を返す。診断の `change` には比較段階と変化した項目だけが入り、審査用ハッシュや各窓の途中サンプルは入らない。従来の広い理由が同じでも、再観測でUIAの失敗コードまたはルートの有効状態が変わった場合は差分を返す。候補成功・失敗の応答形式とPowerShell引数を維持した。

Coreは681件合格。0.1.14の観測比較4ケースは、旧判定に加えて段階と差分種類も検査する形に拡張した。他の既存ケースの欠落は0、純増20件。ビルドの警告・エラーは0で、試験の失敗・スキップも0。ログは `logs/core-final-20261120/summary.json`。

## 専用WinFormsでの観測

独自のUIAプロバイダーを用いず、ログイン窓が背後窓に所有される、背後窓がログイン窓に所有される、双方が未所有の3構成を試した。各構成で `Form.Enabled=false` とした場合はWin32・UIAともに無効。WinFormsの `Enabled=true` を保ち、表示後の対象HWNDに `EnableWindow(false)` を適用した場合は、3構成ともWin32が無効、UIAが有効だった。実際の対象アプリの失敗原因が同じかは、0.1.15での診断が必要。

| 候補取得の試験 | 観測した結果 |
|---|---|
| 通常の無効な背後窓 | 既存の所有3構成と標準・カスタム欄を確認 |
| Win32無効／UIA有効で、認証候補がない背後窓 | `uia-root-enabled-mismatch` と `review-required`。構成を指定した標準・カスタム欄は `candidate-only` |
| 上記の不一致を含む構成で、未確認または通常無効構成の旧ハッシュを指定 | `layout-unproven` |
| 通常の無効状態と、食い違いがある状態で、それぞれ背後窓の深さが上限超過 | `background-structure-unproven`。失敗窓は `background`、詳細は `uia-depth-limit`、上限16に対し到達を試みた深さ17。構成ハッシュなし |
| 食い違いがあり、背後窓に `IsPassword=false` でUIA上も無効なEdit欄がある | `background-authentication-ui`。失敗窓は `background`、構成ハッシュなし |
| 未知の所有元、有効な背後窓、候補が複数、標準パスワード欄を持つ背後窓、別PIDのHWND | 従来どおり候補取得を拒否 |

候補取得試験で画像や登録資材は作成されず、製品ファイルは不変だった。診断の応答に背後窓の架空のタイトル、名前、可変テキスト、値が出ないことを確認した。観測中のグラフ、UIA構造や有効状態の変化で候補を拒否して差分だけを返すことはCoreで検証した。

## 追加の再生耐性試験

既存の専用WinFormsと実際のWindows再生処理を使用する。表示・有効化の遅れ、表示中の別画面、要素候補の重複は、再生しながら状態を観測し、操作回数と停止理由を確認する。実画面を使う追加試験は明示指定で実行する。録画に追記する項目は操作時に観測できる状態に限り、待機上限や安定時間は再生設定に記述する。

- `ReplayRobustness` の実入力試験は13件に合格。遅延表示・タイトル変化・最小化・モーダル・ボタンの非表示と枠外・一時無効では、有効な対象が安定した後に一度だけクリックした。重複、待機上限、取消、実行直前に無効となった場合は入力を送らず停止した。通常のDesktop／Allからは追加試験を分けた。
- Coreは703件に合格し、台帳は473メソッド、786引数行。ウィンドウのDPI・有効／最小化と、UI Automationが報告した画面外状態をAI向け手順書で確認した。ログは `logs/replay-robustness-20261121-recheck/` と `logs/replay-robustness-core-20261121/` に保存した。導入済み0.1.10は専用試験の後に常駐を復元した。
- 遅延表示は起動後に画面が現れる条件を再現した。アプリのプロセス起動時間、個別業務アプリの操作、別解像度・別DPIの実機構成はこの追加試験の範囲外。
